PRINCIPIOS FUNDAMENTAIS DE TESTE (VLADIMIR KHORIKOV - "UNIT TESTING"):
================================================================================
1. DEFINIÇÃO DO SUT (System Under Test):
   - A classe `{service_file}` é o SUT (o sistema que está sendo testado).
   - Colaboradores são as dependências injetadas no construtor (TypeORM Repositories, serviços externos, etc.).

2. REGRA DE OURO INEGOCIÁVEL (ANTI-CHEAT / PROIBIÇÃO DE MOCKAR O SUT):
   - É TERMINANTEMENTE PROIBIDO usar `jest.spyOn(service, ...)` ou substituir métodos da própria classe em teste por mocks.
   - NUNCA mocke o método que você quer testar! O método sob teste DEVE EXECUTAR SUA LÓGICA REAL.
   - Você DEVE mockar EXCLUSIVAMENTE as dependências externas injetadas no construtor.
   - O arquivo de implementação `{service_file}` é ESTRITAMENTE SOMENTE LEITURA. Não altere nada nele.

3. METODOLOGIA GIVEN-WHEN-THEN (ARRANGE-ACT-ASSERT):
   Estruture cada teste obrigatoriamente em 3 partes claras:
   - // Given (Arrange): Configure o retorno esperado dos mocks das dependências (ex: `tattooRepository.findOne.mockResolvedValue(...)`).
   - // When (Act): Chame o método REAL do serviço (ex: `const result = await service.reclassify(adminId, tattooId);`).
   - // Then (Assert): Verifique o resultado retornado E certifique-se de que as dependências foram chamadas com os parâmetros corretos (`expect(tattooRepository.findOne).toHaveBeenCalledWith(...)`).

4. CENÁRIOS OBRIGATÓRIOS PARA CADA MÉTODO PÚBLICO:
   - Cenário de Sucesso (Happy Path): Quando todos os colaboradores retornam dados válidos, a lógica do método deve ser executada até o fim e retornar o resultado correto.
   - Cenários de Falha / Exceções (Sad Path): Quando um colaborador retorna `null` ou falha, verifique que o serviço lança a exceção esperada com `await expect(service.metodo(...)).rejects.toThrow(NomeDaExcecao);`.

5. REGRAS CRÍTICAS DE TYPESCRIPT / JEST:
   - Em TypeScript estrito, NUNCA chame `.mockResolvedValue()` sem argumentos. Se a função retornar void ou undefined, passe explicitamente: `.mockResolvedValue(undefined)` ou `.mockResolvedValue(null)`.
   - Para repositórios do TypeORM, mocke `.findOne.mockResolvedValue(null)` para cenários de não encontrado e `.find.mockResolvedValue([])` para listas vazias.
   - Mantenha estritamente os tipos e contratos das entidades e DTOs.

6. PRESERVAÇÃO DOS MOCKS DO SCAFFOLD:
   - NUNCA altere as declarações `let <dependencia>: any;` para tipos de classe específicos. O tipo DEVE ser mantido como `any` para evitar erros de compilação com propriedades privadas do TypeScript.
   - Todos os métodos de colaboradores chamados pelo serviço (ex: `.create`, `._getPresignedUrl`, `.classifyTattoo`) JÁ FORAM inicializados com `jest.fn()` no `beforeEach`. Use-os diretamente nos testes sem recriar os objetos!
